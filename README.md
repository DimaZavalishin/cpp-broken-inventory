# Практика C++: сломанный инвентарь

Вам передали рабочий по сборке, но неверный по поведению игровой инвентарь.
Нужно разобраться в чужом коде, найти ошибки и исправить их по требованиям.
Темы: классы, инкапсуляция, публичное наследование, виртуальные методы,
override, указатели, std::vector, поиск, граничные случаи и тестирование.

## Модель и правила времени жизни

`Inventory` хранит `Item*`, но **не владеет предметами**. Создавайте Weapon,
Armor и Potion как локальные объекты раньше инвентаря. Объекты должны
существовать при каждом обращении к ним через инвентарь. Не возвращайте
инвентарь с адресами локальных предметов из функции.
Удаление и очистка убирают только указатели, сами предметы продолжают жить.
Не нужны new, delete, умные указатели, clone и специальные операции перемещения.
Копирование инвентаря и предметов в задание не входит.

## Требуемое поведение

1. Item хранит имя и количество. Отрицательное количество в конструкторе
   и setQuantity превращается в 0. Имя сохраняется без изменений, включая пустое.
2. Weapon, Armor, Potion публично наследуют Item. Урон, защита и лечение
   доступны через методы чтения; отрицательные значения превращаются в 0.
3. Вызов use через Item* выбирает реализацию фактического класса.
   Используйте virtual и override; поля не должны быть публичными.
4. Item::use возвращает `Item: <имя>`, Weapon — `Attack: <имя>`,
   Armor — `Equip: <имя>`. Они не изменяют количество, даже если оно равно 0.
5. Potion::use при количестве больше 0 уменьшает его ровно на 1 и возвращает
   `Drink: <имя>`. При 0 возвращает `Empty: <имя>` и сохраняет 0.
   Префиксы содержат один пробел после двоеточия.
6. add возвращает true только при добавлении. nullptr и повторный адрес
   отклоняются с false, размер не меняется. Разные объекты с одинаковым именем разрешены.
7. size возвращает число зарегистрированных объектов, а не сумму количества.
8. at возвращает указатель по индексу от 0; вне диапазона — nullptr.
9. find ищет точное совпадение имени с учётом регистра, возвращает первый
   подходящий указатель или nullptr. Порядок совпадает с порядком добавления.
10. remove удаляет указатель по индексу и возвращает true. Неверный индекс
    даёт false без изменений. Порядок остальных элементов сохраняется.
11. useAll вызывает use каждого предмета один раз в порядке хранения
    и возвращает вектор сообщений. Для пустого инвентаря результат пустой.
12. clear делает инвентарь пустым; повторная очистка безопасна.

## Работа

1. Соберите проект и запустите демонстрацию и начальные тесты.
2. Сопоставьте код с требованиями и исправьте ошибки поведения.
3. Приведите весь собственный код к [соглашению по стилю курса](https://github.com/Flovwvers-students/cpp-course-materials/tree/main/code-style): разделите самостоятельные классы по отдельным заголовкам, исправьте имена методов, функций и полей, форматирование и комментарии. Пояснения перенесите в отчёт.
4. Переименуйте публичные операции по соглашению курса и обновите все вызовы в демонстрации и тестах. Имена классов сохраняйте. Тесты можно менять для нового интерфейса и стиля, но нельзя удалять или ослаблять проверки ради успешного результата.
5. Дополните tests.cpp: проверьте каждый пункт, пустой инвентарь, nullptr,
   дубликат адреса, одинаковые имена, отрицательные характеристики, нулевое
   количество зелья, неверные индексы и удаление первого/среднего/последнего.
6. Покажите вызовы через Item* и объясните время жизни объектов.

## Сборка (C++17, CMake 3.16+)

Установите компилятор C++ (например, Visual Studio с компонентом
«Разработка классических приложений на C++») и CMake.
Из каталога проекта выполните:

```sh
cmake -S . -B build
cmake --build build --config Debug
ctest --test-dir build -C Debug --output-on-failure
```

Демонстрация: `build/Debug/inventory_demo.exe` для Visual Studio;
для генератора с одной конфигурацией — `build/inventory_demo`.
Начальные тесты намеренно не проходят на исходнике. Они не покрывают всё условие.

## Что сдавать

В своём форке задания: исправленный код, дополненные тесты,
краткий отчёт «ошибка → причина → исправление → проверка», описание изменений стиля и команды сборки.
Сдавайте работу через Pull Request по инструкции ниже. Не добавляйте build и исполняемые файлы.
Готовность: сборка успешна, ваши тесты проходят, все требования выполнены,
на защите вы объясняете полиморфизм и почему Inventory не удаляет предметы.

## Как сдать через форк и Pull Request

**Форк** — ваша копия репозитория на GitHub. В ней вы сохраняете решение.
**Pull Request (PR)** — запрос на рассмотрение ваших изменений в исходном
репозитории. Он позволяет преподавателю увидеть разницу и оставить замечания.
В этой работе PR используется для проверки: после приёмки преподаватель
закрывает его **без слияния**, чтобы исходное задание оставалось нерешённым.
Форки и PR публичного задания видны другим пользователям GitHub.

### 1. Сделайте форк

1. Войдите в свой аккаунт GitHub и откройте
   [репозиторий задания](https://github.com/Flovwvers-students/cpp-broken-inventory).
2. Нажмите **Fork** вверху страницы.
3. В поле **Owner** выберите свой личный аккаунт, имя репозитория оставьте
   `cpp-broken-inventory`. Достаточно скопировать только ветку `main`.
4. Нажмите **Create fork**. Убедитесь, что адрес новой страницы начинается
   с `github.com/ВАШ-ЛОГИН/`, а под названием указано, откуда сделан форк.
   Если форк уже есть, откройте его — второй создавать не нужно.

### 2. Скачайте свой форк и создайте ветку

Установите Git. В своём форке нажмите **Code → HTTPS** и скопируйте адрес.
Откройте терминал в папке, где будете хранить работу, и выполните:

```sh
git clone https://github.com/YOUR-LOGIN/cpp-broken-inventory.git
cd cpp-broken-inventory
git switch -c ivanov-ivan
```

Замените `YOUR-LOGIN` своим логином, а `ivanov-ivan` — своей фамилией и именем.
Единый шаблон ветки: **`familiya-imya`**, латиницей, строчными буквами,
через дефис, без пробелов. Например: `petrova-anna`.
Все дальнейшие команды выполняйте из папки проекта.

Если продолжаете работу на том же компьютере, повторно клонировать проект
и создавать ветку не нужно: откройте папку и выполните `git switch ivanov-ivan`.

### 3. Сохраните и отправьте решение в свой форк

Исправляйте код, дополняйте тесты и проверяйте сборку командами из раздела
«Сборка». Создайте `REPORT.md` с ФИО, группой, описанием исправлений
и результатами тестирования. Затем выполните:

```sh
git status
git add -A
git diff --cached
git commit -m "Fix inventory and add tests"
git push -u origin ivanov-ivan
```

`git add -A` добавляет новые, изменённые и удалённые файлы. В `git status` и
`git diff --cached` проверьте состав изменений, включая новые заголовки и удаление
старых файлов. Не добавляйте папку сборки, исполняемые файлы и посторонние данные.
`origin` должен указывать на **ваш форк**: это можно проверить командой
`git remote -v`. При первом push Git может предложить вход в GitHub через браузер.

### 4. Откройте запрос на проверку

1. Откройте [Pull requests исходного задания](https://github.com/Flovwvers-students/cpp-broken-inventory/pulls)
   и нажмите **New pull request**.
2. Нажмите **compare across forks**, если выбор форка не показан.
3. Выставьте направление сравнения:

   | Поле | Значение |
   |---|---|
   | base repository — куда отправляем запрос | `Flovwvers-students/cpp-broken-inventory` |
   | base — целевая ветка | `main` |
   | head repository — откуда берём решение | `ВАШ-ЛОГИН/cpp-broken-inventory` |
   | compare — ваша ветка | `ivanov-ivan` (ваша фамилия и имя) |

4. Посмотрите список изменений: здесь должны быть ваши исправления и тесты.
   Если изменений нет, проверьте выбранную ветку и выполнение `git push`.
5. Нажмите **Create pull request**. Заголовок оформите так:
   `Иванов Иван — группа НАЗВАНИЕ — Инвентарь C++`.
6. В описании укажите ФИО и группу, что исправлено, какие тесты добавлены,
   команды и результаты проверки, оставшиеся вопросы. Если автоматически
   появился шаблон, заполните его.
7. Нажмите **Create pull request** для отправки и сохраните ссылку на PR.
   Для готовой работы создавайте обычный PR, не Draft.

### 5. Исправляйте замечания в той же ветке

Читайте комментарии преподавателя во вкладках **Conversation** и **Files changed**.
После исправлений повторно запустите тесты и выполните:

```sh
git switch ivanov-ivan
git add -A
git commit -m "Address review comments"
git push
```

Изменения автоматически появятся в **том же PR**. Новый PR на каждое
исправление не создавайте. Ответьте на замечания, кратко объяснив изменения.
До завершения проверки сохраняйте форк и ветку. Преподаватель явно сообщает
о приёмке и закрывает PR без слияния; само по себе закрытие PR не означает зачёт.

Справка GitHub: [создание форка](https://docs.github.com/en/pull-requests/how-tos/work-with-forks/fork-a-repo)
и [Pull Request из форка](https://docs.github.com/en/pull-requests/how-tos/create-pull-requests/creating-a-pull-request-from-a-fork).
